Controller parameters

[Blocking, about 10 ms per parameter] Firmware with INFRABOT_CAP_PARAMETERS (protocol 1.1): the gravity, impedance and admittance settings that the touchscreen sliders change.

Every parameter describes itself (name, unit, range, default, slew rate), so no table is compiled into the SDK. set_parameter() stores the requested value and the controller slews its applied value toward it, so a write never steps a gain. Values live in RAM and return to their defaults at reboot. Reading is open to any PC; writing needs the PC that controls the arm, or no controlling PC.

Detailed Description

The client for one arm controller.

One Robot per controller. It owns two UDP sockets and two threads: a receive thread that parses telemetry and replies, and a 1 kHz service thread that sends the heartbeat, keeps the NRT session alive and runs the native joint stream. Functions are thread-safe unless noted.

A program follows the groups below in order: connect(), wait for fresh telemetry, set_motor_profile(), servo_on(), switch_mode() into the mode it needs, commands or moves, then stop() (the arm holds, enabled) or servo_off(), and disconnect().

[Blocking, timeout] Clears the drives that report a fault.

A faulted drive (over-voltage, over-temperature, lost CAN and so on) no longer follows commands. RobotState::joints.drive_state shows the code, and fault_log() says why and what to do. Remove the cause, then servo_off() the group if it is still enabled, clear_fault() and servo_on() again.

Only disabled drives are cleared; an enabled faulted drive is refused. The call waits until no cleared drive reports a fault.

◆ connect()

bool infrabot::Robot::connect ( std::string &  error)

[Blocking, up to 0.5 s] Opens the link: negotiates the protocol, then starts the heartbeat.

Call it before anything that talks to the controller (start_serial_log(), download_mcu_log() and the firmware update functions work without it). It binds telemetry_port on this PC, asks the controller for its identity and capabilities (then in info()), registers for telemetry and starts the receive and service threads. Calling it again reconnects from scratch.

Success means the controller answered the handshake; telemetry follows a few milliseconds later. The setup and power calls refuse telemetry older than 100 ms, so wait until state().telemetry_age_ms is below 100 before calling them.

A V1-only controller is treated as protocol 1.0 with unknown firmware. A different major version or no valid reply fails.

Postcondition
The receive and service threads run and telemetry starts to arrive.
See also
info(), state(), disconnect()
Parameters
[out]errorWhy it failed.
Returns
true when connected.

◆ disconnect()

void infrabot::Robot::disconnect ( )

[Blocking] Closes the link: stops the threads and closes the sockets.

Call it when the program is done with the controller; the destructor calls it too, and a second call does nothing. A native joint stream ends with it. state() keeps the last values, with connected false.

Nothing is sent: the controller is not told.

Warning
In IDLE, RT and NRT modes the controller misses the PC after 100 ms, makes a controlled stop and holds the arm enabled; a local mode (gravity compensation, impedance, admittance) keeps running without a PC. Call stop() first to leave the arm still, or servo_off() to power it down.

[Blocking, a few s] Downloads the controller's run log into two new files.

◆ fault_log()

std::vector< FaultEvent > infrabot::Robot::fault_log ( ) const

[Non-blocking] Faults, stops, self-checks and link warnings, oldest first, at most 200.

The receive thread adds an event when a drive fault appears or clears, a controlled stop is latched, a self-check result arrives or the link is poor. Each FaultEvent has a Chinese message with the probable cause and what to do. Read it after a failure to see what happened, even when the state has changed since. The log lives as long as the Robot.

[Blocking, 1 s] Moves the gripper, in any control mode (also during movej/movep).

The gripper moves to the position at the speed limit and stops pushing at the force limit, so closing on an object grips it with that force. [Blocking] Moves J1–J7 to position in NRT_JOINT.

◆ switch_mode()

bool infrabot::Robot::switch_mode ( Mode  mode,
std::string &  error 
)

[Blocking, 2 s] Switches the controller's control mode.

RT modes follow a stream from the PC (servej(), servep()). NRT modes run point-to-point moves (movej(), movep()). The local modes (gravity compensation, impedance, admittance) run on the controller by themselves. A mode other than IDLE is entered from IDLE with the arm enabled and still; to change modes, go back through IDLE with stop() or switch_mode(Mode::Idle).

RT modes: the caller then streams servej() or servep() starting from hold_command(). NRT modes: the SDK starts the movej/movep session, holding the current command, and keeps it alive until the mode changes.

While another program on this PC stopped sending less than 0.5 s ago, or a stopped local mode is still handing its gains back, the controller answers busy; the call retries for up to 1 s. If the controller does not answer at all (outcome unknown), the SDK asks for a controlled stop.

Precondition
IDLE, the arm enabled, every joint below 0.05 rad/s.
Postcondition
hold_command() holds what the arm holds now.
See also
stop(), resume(), hold_command()
Parameters
modeThe mode to enter.
[out]errorWhy it failed.
